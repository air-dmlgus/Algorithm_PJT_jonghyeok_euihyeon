# 자료구조·알고리즘 기획 및 고찰

## 문제 정의

음식과 회원은 ID로 자주 찾고, 식단·게시글은 시간 순으로 훑는 일이 많다. 음식명/게시글은 부분 문자열 검색이 필요하며, 식단은 영양 수치 정렬, 추천은 전체 후보 중 소수의 상위 결과만 필요하다. 따라서 모든 기능을 하나의 List 선형 탐색으로 처리하지 않고 접근 패턴별 구조와 알고리즘을 선택했다.

## 자료구조 선택

| 번호 | 데이터/기능 | 구조 | 시간 복잡도 | 선택과 고찰 |
|---|---|---|---|---|
| DS-01 | 회원/음식 ID 인덱스 | LinkedHashMap | 조회 평균 O(1) | HashMap 성능과 재현 가능한 출력 순서를 함께 얻음. 해시 충돌 최악 O(n) |
| DS-02 | 식단·챌린지·글·댓글 | ArrayList | 순회 O(n), 끝 삽입 분할상환 O(1) | JSON 배열과 자연스럽게 대응. 중간 삭제는 O(n)이나 교육용 규모에 적합 |
| DS-03 | 팔로우 | LinkedHashSet | 추가/삭제/포함 평균 O(1) | 중복을 구조적으로 차단하고 표시 순서를 보존 |
| DS-04 | Top-K 음식 추천 | PriorityQueue | 전체 O(n log k), 메모리 O(k) | 전체 정렬 O(n log n)보다 k가 작을 때 효율적 |

## 적용 알고리즘

### Algo-01 영양 점수

식단 항목별 `영양소 × 섭취 횟수`를 O(e)에 합산한다. 사용자 기초대사량 추정치의 1/3을 한 끼 목표로 삼고 열량 편차, 단백질 부족, 나트륨 과다, 지방 에너지 비율을 감점해 0~100점으로 제한한다. 수치가 설명 가능하고 API 없이 재현되지만, 의료 모델이 아니며 활동량·알레르기·검사 결과를 반영하지 못한다.

### Algo-02 KMP 부분 문자열 탐색

음식명과 게시글 제목+본문에 KMP를 적용했다. 패턴 전처리는 O(m), 각 문자열 검색은 O(n+m)이며 불일치 때 이미 비교한 접두사를 건너뛴다. 짧은 한글 데이터에서는 단순 탐색이 더 빠를 수도 있지만, 비교 횟수를 직접 계측할 수 있고 최악 시간 경계를 보장한다. Java `char` 단위이므로 이모지처럼 보조 평면 문자는 코드 포인트 단위 개선 여지가 있다.

### Algo-03 병합 정렬

본인 식단을 열량 오름차순으로 정렬한다. 시간 O(n log n), 추가 메모리 O(n), 안정 정렬이다. 구현에서 두 부분 배열 원소를 비교할 때마다 카운터를 올린다. 작은 입력은 삽입 정렬이 캐시 효율에서 유리할 수 있어 향후 하이브리드 정렬을 고려할 수 있다.

### Algo-04 우선순위 큐 Top-K 추천

단백질을 가산하고 나트륨·목표 열량 편차를 감산하며, 고혈압 표기 사용자는 나트륨 패널티를 확대한다. 크기 k의 최소 힙을 유지해 n개 후보를 O(n log k)에 처리한다. 규칙은 설명 가능하지만 선호·알레르기를 아직 반영하지 않으므로 실제 서비스에서는 필터를 먼저 적용해야 한다.

## 성능 측정 방법과 예시

`System.nanoTime()`으로 알고리즘 구간만 재고, KMP는 문자 비교, 병합 정렬은 원소 비교, 추천은 후보 평가 횟수를 센다. 로그인 후 `7.성능 데모`를 실행하면 다음 형식으로 현재 환경의 값을 얻는다.

```text
KMP 결과 2건 / KMP 부분 문자열 탐색 O(N+M) | 실행시간 123,456ns | 비교 19회
병합 정렬 결과 3건 / 병합 정렬 O(n log n) | 실행시간 87,000ns | 비교 3회
추천 결과 5건 / 우선순위 큐 Top-K 추천 O(n log k) | 실행시간 310,000ns | 비교 15회
```

위 숫자는 출력 형식 예시이며 실제 측정값은 JVM 워밍업, JIT 컴파일, CPU 상태, 데이터량에 따라 달라진다. 신뢰도 높은 비교에는 동일 JVM에서 워밍업 후 수백 회 반복하고 중앙값·p95를 사용하거나 JMH를 도입해야 한다. 단일 실행시간만으로 결론을 내리지 않고 입력 크기에 따른 비교 횟수 증가가 이론 복잡도와 일치하는지 함께 본다.

## 생성형 AI와 fallback

`GenerativeAiProvider`는 식단 분석과 운동 코칭 계약을 정의한다. 현재 `RuleBasedAiProvider`가 완전 오프라인으로 같은 입력에 재현 가능한 결과를 낸다. `HttpAiProvider`는 실제 모델 연동 시 프롬프트를 만들고 `complete()`만 공급하도록 분리했다. 실제 연동 시 API 키 환경 변수, 시간 제한, 재시도, 출력 스키마 검증, 개인정보 최소화, 비용 한도와 규칙 기반 자동 fallback이 추가되어야 한다.

## 결론

교육용 데이터 규모에서는 대부분의 방법이 충분히 빠르지만, 선택 근거와 측정 가능성을 코드에 드러내는 것이 핵심이다. Map/Set으로 무결성과 조회 성능을 확보하고, KMP·병합 정렬·힙으로 서로 다른 문제 유형을 명시적으로 해결했다. 다음 단계는 대규모 합성 데이터와 JMH 벤치마크, 알레르기 hard filter, 비밀번호 해시, 데이터베이스 트랜잭션 도입이다.
